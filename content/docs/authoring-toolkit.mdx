## Lab header and score

Put the header and the score at the top of every lab. The score adds up every graded element on the page that shares its `labId`: quizzes, fill in the blanks, short answers and the autograder. The total is worked out for you, so there is no number to keep in sync. Try the demos below and watch it move.

<LabHeader
  pillar="Pillar X: Your Pillar Name"
  title="Your Lab Title"
  difficulty="Beginner"
  time="30-45 mins"
  compute="Laptop CPU or Docker"
  author="Your Name"
/>

<LabProgress labId="toolkit-demo" />

```mdx
<LabHeader
  pillar="Pillar X: Your Pillar Name"
  title="Your Lab Title"
  difficulty="Beginner"
  time="30-45 mins"
  compute="Laptop CPU or Docker"
  author="Your Name"
  colabUrl="https://colab.research.google.com/..."   {/* optional */}

<LabProgress labId="your-lab-id" />
```

`difficulty` is `Beginner`, `Intermediate` or `Advanced`. The byline also comes from the page's `author` frontmatter.

## Graded questions

Every question type takes the same three optional props, and they are what make it count toward the score:

- `labId` ties it to the lab's score. Leave it off for a practice question that scores nothing.
- `id` names it within the lab. It defaults to a name made from the question, so set it if you reword the question later.
- `points` is what it is worth. The default is 5.

Full points go to a first-try correct answer. After a wrong answer it is worth half, and a retry can only raise a score, never lower it.

### Multiple choice

<Quiz
  labId="toolkit-demo"
  id="demo-choice"
  question="Why is a plain substring match not enough to catch a leaked secret?"
  options={[
    "Models cannot repeat strings from their prompts.",
    "An attacker can ask for the secret in an encoding such as Base64 or hex.",
    "Substring matching is too slow.",
  ]}
  correctIndex={1}
  explanation="Encoded output no longer contains the secret as plain text, so a naive check passes it."
/>

```mdx
<Quiz
  labId="your-lab-id"
  id="substring"
  points={5}
  question="Your question?"
  options={["Option A", "Option B", "Option C"]}
  correctIndex={1}
  explanation="Why that answer is right."
/>
```

`correctIndex` counts from zero. Every wrong option should be a plausible mistake.

### Fill in the blank

Best for one exact term. The answer is checked ignoring case and spacing, so list every spelling you will accept.

<Blank
  labId="toolkit-demo"
  id="demo-blank"
  prompt="The Python function that returns the length of a list is ___()"
  answers={["len"]}
  explanation="len() returns the number of items in a list, string or other sized object."
/>

```mdx
<Blank
  labId="your-lab-id"
  id="hex-method"
  points={5}
  prompt="The bytes method that returns a hexadecimal string is .___()"
  answers={["hex", ".hex", "hex()", ".hex()"]}
  explanation="bytes.hex() turns each byte into two hexadecimal characters."
/>
```

Put `___` (three underscores) where the blank goes. To accept a pattern instead of fixed words, write it between slashes, such as `"/^b(ase)?64$/i"`.

### Short answer

Best when you want the learner to explain an idea in their own words. It is graded against a rubric: each rubric item is an idea a good answer should contain, with a list of words that show it is there. Points are shared across the rubric, so an answer covering two of three ideas earns two thirds. The learner sees which ideas were covered and which were missing, then your model answer.

<ShortAnswer
  labId="toolkit-demo"
  id="demo-short"
  question="Why is a backup that is never tested a risk?"
  rubric={[
    { label: "You cannot be sure it works", anyOf: ["work", "sure", "certain", "assume", "trust"] },
    { label: "Problems are found too late", anyOf: ["late", "disaster", "emergency", "when you need", "too late"] },
  ]}
  modelAnswer="An untested backup is an assumption. You only learn it is broken when you need it, which is the worst time to find out."
/>

```mdx
<ShortAnswer
  labId="your-lab-id"
  id="rotate"
  points={5}
  minLength={40}
  question="Why should a canary differ for every session?"
  rubric={[
    { label: "A fixed canary can be learned", anyOf: ["learn", "leak", "known", "memor"] },
    { label: "A leak can be traced to a session", anyOf: ["trace", "which session", "unique"] },
  ]}
  modelAnswer="A model answer the learner sees after submitting."
/>
```

This is a keyword check, so say so (the component already does). Write each `anyOf` list to cover the common ways to say an idea, including word stems such as `memor` for memory, memorise and memorised. It will sometimes miss a good answer in unusual words, which is why the model answer is always shown. Do not use it for anything that needs to be exactly right. Use a quiz or the autograder for that.

## In-browser Python runner

The runner loads Python in the browser (Pyodide), runs the learner's code, then runs your test script in the same session. If every `assert` passes, the learner earns all `points`. If a check fails part way, they earn the points printed so far, so print `(5 pts)` at the end of each passing line. It needs the starting code, the test script and the points.

````mdx
<PythonRunner
  labId="your-lab-id"
  points={10}
  initialCode={`def double(x):
    # TODO: return x doubled
    raise NotImplementedError
`}
  testCode={`
assert double(2) == 4, "double(2) should be 4"
print("Test 1 passed (5 pts)")

assert double(-3) == -6, "double(-3) should be -6"
print("Test 2 passed (5 pts)")
`}
/>
````

The test script is plain Python with `assert` and `print`, run after the learner's code, so it can call whatever they defined. Print one line per check, and keep the script deterministic and fast.

See the [worked example](/docs/interactive-tutorial/00-prompt-injection-guard) for a full runner with a real autograder. Keep the test code deterministic and fast.

## Figure beside text

Use `Split` when a diagram or image explains the text next to it. The figure sits on one side and the words on the other. On a phone the figure comes first, then the text.

<Split side="left" size="md">
<SplitMedia caption="A tall diagram keeps its shape.">
<Mermaid chart="
graph TD
  A[Learner reads the writeup] --> B[Learner writes the code]
  B --> C[Autograder runs]
  C -->|all pass| D[Score fills in]
  C -->|a check fails| B
" />
</SplitMedia>
<SplitText>

Put the figure on the left when the picture leads, and the explanation follows it. Anything works in the text column: paragraphs, lists, callouts and maths.

<Callout type="success" title="Good for">
Vertical flowcharts, architecture diagrams and screenshots that are taller than they are wide.
</Callout>

</SplitText>
</Split>

<Split side="right" size="sm" align="center">
<SplitMedia caption="A small figure on the right.">
<Mermaid chart="
graph TD
  X[Input] --> Y[Guard] --> Z[Output]
" />
</SplitMedia>
<SplitText>

Mirror it with `side="right"`, and make the figure smaller with `size="sm"` when it is a minor aid and the text should lead. Use `align="center"` to centre the two columns on each other.

</SplitText>
</Split>

````mdx
<Split side="left" size="md">
<SplitMedia caption="A caption under the figure.">
<Mermaid chart="
graph TD
  A[Start] --> B[Finish]
" />
</SplitMedia>
<SplitText>

Your text goes here. Leave a blank line after the opening tag
so Markdown works inside.

</SplitText>
</Split>
````

- `side` is `left` or `right`: where the figure sits.
- `size` is `sm` (a third of the row), `md` (five twelfths) or `lg` (half).
- `align` is `start` (default) or `center`.

For an image, put it inside `SplitMedia` in place of the diagram. Save the file in the `public/images` folder and refer to it as `/images/your-lab/figure-1.png`. Always add alt text.

````mdx
<SplitMedia caption="What the learner sees.">
![The autograder output showing four passing checks](/images/your-lab/autograder.png)
</SplitMedia>
````

## Colour rule

Keep the page monochrome with one accent, and use colour only for meaning:

- **Red** for attacks, red-team prompts and failing tests.
- **Green** for defences, patches and passing checks.
- **Amber** for threat-model notes, thresholds and caveats.
- **Magenta** for navigation, links and buttons, and nothing else.

Never give each pillar its own colour.

## The compute rule

<Callout type="info" title="Every lab must fit one of three budgets">
A laptop (CPU or Docker), a free Colab T4 in under 15 minutes, or a free API tier or local model. Anything that needs pre-training from scratch, a multi-GPU cluster or real H100 hardware is cut or turned into a simulation. Check the [roadmap](/docs/roadmap) for the budget your topic has been given.
</Callout>

## Workflow

<Steps>
<Step>
### Claim a lab

Pick a planned lab on the [roadmap](/docs/roadmap) and tell the project lead. Claimed labs are marked on the roadmap and credited on the [Credits](/docs/credits) page.
</Step>

<Step>
### Branch

```bash
git checkout -b feature/pillar-X-module-name
```
</Step>

<Step>
### Put the files in the right place

<Files>
  <Folder name="content" defaultOpen>
    <Folder name="docs" defaultOpen>
      <Folder name="pillar-X-your-pillar" defaultOpen>
        <File name="NN-your-lab.mdx" />
      </Folder>
    </Folder>
  </Folder>
  <Folder name="labs" defaultOpen>
    <Folder name="pillar-X" defaultOpen>
      <Folder name="NN-your-lab" defaultOpen>
        <Folder name="starter">
          <File name="challenge.py" />
          <File name="requirements.txt" />
        </Folder>
        <Folder name="tests">
          <File name="test_challenge.py" />
        </Folder>
        <Folder name="solution">
          <File name="challenge_solution.py" />
        </Folder>
      </Folder>
    </Folder>
  </Folder>
</Files>

The writeup lives under `content/docs`. The code and the tests live under `labs`. The solution folder is optional but recommended.
</Step>

<Step>
### Write the lab

Copy the [module template](/docs/template-module), then use the [authoring toolkit](/docs/authoring-toolkit) to add a quiz, hints, a reference solution or an in-browser runner. In the frontmatter, add `author: "Your Name"` and your byline appears on the page.
</Step>

<Step>
### Test it

```bash
pnpm dev                          # preview the writeup
cd labs/pillar-X/NN-your-lab
pip install -r starter/requirements.txt
pytest tests/                     # run the autograder
```
</Step>

<Step>
### Open a pull request

Push your branch and open a PR. A reviewer will use the checklist below.
</Step>
</Steps>

## Review checklist

A lab is ready to merge when:

- The threat model names an attacker, what they can do, and why obvious defences fail.
- It runs inside one of the three compute budgets, and says which.
- `pytest` fails on the starter code and passes on the solution.
- Every test has a one-line docstring saying what it proves.
- Every quiz answer has an explanation, and every hint helps without giving the answer away.
- Red is used for attacks and failures, green for defences and passes, amber for caveats. Nothing else gets a colour.
- It ends with a "Go deeper" section linking to papers or courses.

## Questions

<Accordions>
  <Accordion title="Can I add a new pillar topic that is not on the roadmap?">
    Yes. Open an issue describing the threat model and the compute budget first. If it fits one of the three budgets, it can go on the roadmap.
  </Accordion>
  <Accordion title="Do I have to build the in-browser runner?">
    No. A writeup, starter code and a pytest suite is a complete lab. The in-browser runner is for labs small enough to run in Python in the browser.
  </Accordion>
  <Accordion title="How do I get credited?">
    Put `author: "Your Name"` in the lab's frontmatter and add yourself to the [Credits](/docs/credits) page in the same pull request.
  </Accordion>
  <Accordion title="Where do I ask for help?">
    Message the project lead, or open a draft pull request and ask there.
  </Accordion>
</Accordions>
